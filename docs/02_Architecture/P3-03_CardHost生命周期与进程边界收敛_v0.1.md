## 1. 目标与决策边界

用户已确认：每个交互式用户会话一个独立 CardHost 进程，承载该会话全部独立卡片。主应用可以退出；当全局“主程序退出后保留卡片”开关开启时，CardHost 继续显示卡片；开关关闭时，卡片全部关闭且 CardHost 退出。

本文件的目标：
- 将进程职责、启动/退出路径和会话边界具体化。
- 识别 IPC、持久化、故障恢复、部署升级等必须明确的接口契约。
- 给出可验证的异常矩阵与 P3 后续工作包。
- 将未决技术项与已确认决策严格分开。

不在本轮确定：Supervisor、即时崩溃恢复 SLA、Named Pipes、数据库、.NET 运行时、WPF/WinUI、桌面层 API 或目标系统兼容性结论。

## 2. 进程与模块边界

| 边界 | 主要职责 | 不应承担 |
|---|---|---|
| FolderHub Main Process | 主界面、托盘、设置、分类/文件夹管理用例；CardHost 生命周期管理；会话发现与 IPC 客户端 | 不直接承载独立卡片窗口的长期生命周期 |
| CardHost Process | 当前会话全部卡片窗口的创建、显示、更新、关闭；卡片交互事件；主应用退出后的独立托管 | 不承接主界面、分类管理等完整业务 UI |
| Domain / Application | 路径唯一性、分类/文件夹业务规则、卡片启停用例、退出策略判断 | 不依赖 HWND、COM、WorkerW 或具体 IPC |
| Persistence Adapter | 配置、卡片元数据、位置/锁定状态持久化 | 不绑定某一数据库/文件格式 |
| Windows Desktop Adapter | 桌面层级、窗口位置、透明度、DPI/显示器、托盘/启动和 Shell 操作 | 不向领域层泄漏平台句柄和 API 细节 |
| IPC Contract | 命令、事件、错误、会话身份和协议版本 | 不成为业务规则的第二实现 |

### 2.1 会话隔离约束

- 一个交互式用户会话最多一个有效 CardHost。
- 不同用户会话之间不得共享卡片窗口或未授权状态。
- CardHost 以当前交互用户身份运行；不使用 LocalSystem/Windows Service 托管可见 UI。
- 主应用启动时应先发现当前会话既有 CardHost，再决定复用或启动，避免双宿主。
- 用户注销/会话结束后，CardHost 随该会话终止；下次登录按持久化状态恢复。RDP 断开与注销必须区分并实测。

## 3. 生命周期状态模型（逻辑层）

| 状态 | 含义 | 允许的转移 |
|---|---|---|
| ABSENT | 当前会话没有 CardHost | STARTING |
| STARTING | 进程已启动，尚未完成握手 | READY / FAILED |
| READY_ATTACHED | CardHost 就绪且主应用已连接 | READY_DETACHED / STOPPING / FAILED |
| READY_DETACHED | 主应用已退出，CardHost 独立托管卡片 | READY_ATTACHED / STOPPING / FAILED |
| STOPPING | 正在关闭卡片、落盘并退出 | ABSENT / FAILED |
| FAILED | 宿主异常终止或不可用 | 主应用重启后重新发现/重建；是否即时恢复待决 |

状态名称是逻辑模型，不等于具体进程 API 或实现状态码。

## 4. 关键时序

### 4.1 主应用启动与连接

1. Main Process 读取配置和当前用户会话标识。
2. 查询当前会话 CardHost 是否存在。
3. 若不存在，启动一个 CardHost；若存在则尝试连接，不重复创建。
4. 执行身份/会话校验、协议版本协商和能力协商。
5. 发送卡片配置快照及增量版本；CardHost 按稳定卡片 ID 幂等创建/更新。
6. CardHost 返回当前卡片状态和配置版本，主应用完成状态对账。

### 4.2 主应用退出且保留开关开启

1. Main Process 停止接收新的 UI 操作并冻结退出时配置快照版本。
2. 发送 `DETACH_AND_KEEP` 语义命令，携带请求 ID、会话 ID 和配置版本。
3. CardHost 校验版本、完成待处理状态持久化，并确认卡片处于独立托管状态。
4. Main Process 收到确认后退出；CardHost 转为 `READY_DETACHED`。
5. 若命令失败/超时，不得静默假装成功；需按可诊断错误路径提示或取消退出，具体 UX 留待后续设计。

### 4.3 主应用退出且保留开关关闭

1. Main Process 发送 `CLOSE_ALL_AND_STOP`。
2. CardHost 关闭全部卡片，提交最后状态并返回完成/失败结果。
3. 成功后 CardHost 退出，Main Process 完成退出。
4. 若 CardHost 无响应，需有超时、用户可理解的反馈及残留进程清理策略；强制终止条件留待 P4。

### 4.4 主应用再次启动

- 若 CardHost 仍处于 `READY_DETACHED`，重新连接并切换到 `READY_ATTACHED`。
- 若 CardHost 不存在，从持久化配置恢复卡片。
- 若发现多个 CardHost，进入诊断/恢复流程，不得无差别创建重复卡片。

## 5. IPC 契约要求（不指定技术）

最低消息类别：
- `HELLO` / `HELLO_ACK`：身份、会话、协议版本和能力协商。
- `SYNC_SNAPSHOT` / `SYNC_DELTA`：配置快照/增量同步，带版本号。
- `UPSERT_CARD` / `REMOVE_CARD`：卡片增删改，按卡片 ID 幂等。
- `DETACH_AND_KEEP`：主应用退出但卡片继续托管。
- `CLOSE_ALL_AND_STOP`：关闭全部卡片并退出宿主。
- `CARD_STATE_CHANGED`：位置、锁定、可见性等状态变化回报。
- `HEALTH_PING` / `HEALTH_PONG`：可用性探测。
- `ERROR`：结构化错误码、可重试标志和关联请求 ID。

共同要求：
- 同一用户会话和用户身份约束；明确 IPC ACL/权限边界。
- 消息带协议版本、请求 ID、会话 ID；需要重试的命令具备幂等语义。
- 明确超时、取消、重连、重复消息、乱序消息及版本不兼容处理。
- 不能只依赖进程名或可伪造的客户端字段进行身份认证。
- Named Pipes 是候选，不是已选技术；需在目标 OS 验证访问控制与 API 可用性。

## 6. 持久化和状态所有权

当前必须解决的核心矛盾：主应用退出后，CardHost 仍允许用户拖动卡片、锁定位置或改变卡片可见状态，因此状态更新不能依赖已退出的 Main Process。

候选规则（待 P3-04 细化）：
1. FolderHub 主应用拥有业务配置管理入口；卡片窗口状态由 CardHost 在窗口交互发生时产生。
2. CardHost 必须能够通过抽象 Persistence Adapter 保存卡片位置/锁定状态，即使 Main Process 已退出。
3. 主应用连接时，双方通过配置版本/状态版本对账；不得用旧快照覆盖较新的 CardHost 窗口状态。
4. 对同一字段定义唯一写入者或明确版本冲突解决规则；不得采用无协调的双写。
5. 存储技术、事务、备份、迁移和损坏恢复策略均未选定。

## 7. CardHost 故障恢复候选

| 方案 | 行为 | 收益 | 代价 | 当前结论 |
|---|---|---|---|---|
| R1 下次启动恢复 | CardHost 崩溃后不保留监督进程；用户下次启动主应用时检测并恢复卡片 | 最少进程、部署和权限复杂度 | 主应用退出期间崩溃后卡片不会即时恢复 | 优先验证候选，不视为批准 |
| R2 轻量 Supervisor | 每会话增加监督进程，CardHost 异常时自动重启 | 可在主应用退出期间即时恢复 | 增加第三进程、生命周期、崩溃风暴和升级复杂度 | 暂不采用；先证明需求收益 |
| R3 Windows Service + GUI Agent | 服务负责机器级监督，用户会话 Agent 显示卡片 | 可处理机器级后台任务 | Session 0、服务安装权限、会话代理和安全复杂度高 | 不推荐；当前无机器级服务需求 |

首版验证原则：先验证 R1 是否足以满足已批准 SRS 的可靠性/验收约束。若 SRS 未规定主应用退出期间卡片崩溃后必须即时恢复，不得自行增加即时恢复要求；若发现存在明确缺口，应提出影响分析和用户澄清，而不是把 R2 自动写入设计基线。

## 8. 异常与恢复验证矩阵

| 场景 | 预期处理原则 | 验证证据 |
|---|---|---|
| CardHost 启动失败 | 主应用报告失败，不显示虚假“卡片已就绪” | 启动失败日志/用户反馈 |
| 主应用重复启动 | 发现并复用当前会话宿主 | 进程/卡片唯一性检查 |
| IPC 中断 | 检测连接丢失，保留可恢复状态，重连不重复执行非幂等操作 | 断连/重连测试 |
| 主应用退出时 IPC 超时 | 不静默宣称退出策略完成；给出明确失败处理 | 超时测试 |
| CardHost 异常终止 | 持久化状态可恢复；R1/R2 恢复差异实测 | 崩溃注入测试 |
| 卡片增删改并发 | 版本/幂等策略避免丢失或重复 | 并发操作测试 |
| CardHost 与主应用版本不一致 | 协议协商失败时安全降级/提示 | 版本错配测试 |
| Explorer 重启 | 卡片桌面层级恢复或进入可诊断失败状态 | Explorer 重启测试 |
| 显示器/DPI 改变 | 依 ADR-033 分别恢复主组件和每张卡片位置 | 多显示器/DPI 测试 |
| RDP 断开/重连 | 不将断开误判为用户注销；恢复后卡片可见性符合会话状态 | RDP 测试 |
| 用户注销/关机 | CardHost 随会话结束；下次登录按配置恢复 | 注销/关机测试 |
| 升级/回滚 | 同会话不并存不兼容宿主；状态可迁移或保留 | 升级/回滚测试 |

## 9. 资源、部署与维护边界

- 每个交互用户会话固定一个 CardHost，不随卡片数线性增加进程。
- 卡片数量、窗口资源、GDI/USER 对象、句柄泄漏和 CPU/内存基线需通过 P3/P4 测试确定，不在当前凭空设数。
- 主应用和 CardHost 版本应协调发布；安装升级需处理旧宿主退出、协议版本兼容和用户配置保留。
- 用户级启动入口由主应用负责；CardHost 是否随主应用登录启动或按需拉起待验证。
- 不使用机器级服务作为默认部署依赖；权限保持普通用户级，若后续需要提升权限必须重新做安全评估。
- 诊断至少记录会话 ID（脱敏/安全处理）、进程版本、宿主状态、IPC 错误码和恢复结果；不得记录敏感路径之外的无关数据。
