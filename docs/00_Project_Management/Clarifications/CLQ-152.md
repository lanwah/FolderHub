## 1. 问题背景

Q-010 / ADR-021 已确认产品行为：

1. “主程序退出后是否保留独立卡片”为全局统一开关，默认开启。
2. 开启时，退出 FolderHub 主程序后已创建的独立卡片继续显示。
3. 关闭时，退出主程序后所有独立卡片一并关闭。
4. 不提供逐卡片覆盖设置。

以上产品行为属于已批准需求基线 REQ-BL-1.0 / FR-016 / FR-017 / BR-012，不在本题重新讨论。本题仅确定实现该行为的宿主/进程生命周期候选。

Q-015 原延期目标为 P3 架构方案评审/批准前；该触发条件现已到达。P3-02 已完成候选分析，现提交用户选择。

## 2. 需要确认的问题

**主程序退出后独立卡片继续显示的生命周期应采用何种技术架构？**

| 选项 | 完整描述 | 优点 | 缺点/代价 | 风险/适用条件 |
|---|---|---|---|---|
| A | 一个独立 CardHost 进程承载同一用户会话的全部独立卡片；主应用负责管理和设置；主应用退出时按全局开关决定保留或关闭 | 主应用可真正退出；进程数量固定；多卡片集中管理；主 UI 与卡片故障隔离 | 需要 IPC、状态同步、宿主重连、崩溃恢复和版本协同 | CardHost 崩溃时全部卡片可能同时消失；须验证桌面层级、会话和恢复策略 |
| B | 主窗口关闭，但主应用进程继续后台驻留并托管卡片 | 架构最简单；无需 IPC；资源共享直接 | 主应用进程实际上没有退出；与“退出应用”语义可能冲突；主进程崩溃会关闭全部卡片 | 仅当用户明确接受“关闭主窗口、后台进程继续运行”时适用 |
| C | 每张独立卡片由一个独立进程承载 | 单卡片崩溃可隔离；单卡片可独立重启和诊断 | 进程数随卡片数增长；资源、升级、清理、同步和批量管理复杂 | 只有后续验证证明单宿主隔离不足时再考虑 |
| D | Windows Service 负责后台协调，另由用户会话 GUI Agent 显示卡片 | 适合确有机器级后台任务的产品 | 服务不能直接与用户交互，必须另建 GUI Agent；涉及 Session 0、服务安装权限、会话代理、安全和 IPC | 当前单用户桌面工具没有机器级服务需求，不推荐 |
| E | 其他（请描述不同的宿主/进程模型） | 可容纳上述选项未覆盖的约束 | 需要补充完整的进程、会话、通信、恢复和部署说明 | 方案不完整时无法评估可行性 |

## 3. 助手推荐（非用户决定）

- 推荐选项：**A，一个用户会话一个独立 CardHost 进程**。
- 推荐理由：最直接满足“主应用进程真正退出后，卡片仍继续显示”的产品语义；一个会话一个宿主可避免进程数随卡片数量增长；Windows Service 的交互限制使其不适合直接托管可见卡片。
- 推荐置信度：中高。
- 依据：REQ-BL-1.0 / FR-016 / FR-017 / BR-012；ADR-007 / ADR-021；P3-02 架构候选比较；Microsoft Learn Interactive Services 文档。
- 可能改变推荐的条件：若用户明确允许主应用进程继续后台驻留，则 B 的成本更低；若实测单宿主无法满足卡片故障隔离，则可重新评估 C；若未来出现机器级后台服务需求，再评估 D。

**用户确认选择：A**

- 确认结论：采用“每个交互式用户会话一个独立 CardHost 进程，由该进程承载该会话的全部独立卡片”的进程/宿主模型。
- 主应用职责：管理主界面、托盘、配置和卡片管理用例；负责启动、发现、连接 CardHost，并通过受限 IPC 发送管理命令/配置变更。
- CardHost 职责：在当前交互式用户会话中创建、显示、更新和关闭该会话的全部独立卡片；主应用正常退出且全局保留开关开启时继续运行。
- 关闭语义：全局保留开关关闭时，主应用要求 CardHost 关闭全部卡片并退出；不提供逐卡片覆盖。
- 进程边界：不采用“主窗口关闭但主进程继续驻留”作为该选择的等价实现；不采用每卡片一进程；不采用 Windows Service 直接承载可见卡片。
- 本选择仅确认宿主/进程模型方向，不确认 IPC 技术、数据库、持久化实现、Supervisor/看门狗、安装升级机制、Win32 桌面层 API 或目标 OS 兼容性。
