## 1. 问题背景与影响

ADR-035 已确认 Main Process 与 CardHost 按逻辑聚合划分单一权威写入者，但没有选择数据库和物理存储。需确定持久化后端，以便 P3 收敛架构边界，并为 P4 的表结构、事务、并发、迁移和备份恢复设计提供输入。此选择不修改需求基线，也不改变 ADR-035 的逻辑写入权。

## 2. 提交用户选择的完整选项

| 选项 | 方案 | 优点 | 缺点/代价/风险 |
|---|---|---|---|
| A（推荐） | SQLite 本地数据库；单一数据库承载逻辑聚合，按 ADR-035 保持各逻辑聚合单一写入者；并发写入、事务和物理布局细节在 P4 明确 | 本地嵌入式、部署简单；事务和数据迁移机制成熟；适合结构化配置/状态数据；便于备份与完整性检查 | SQLite 写并发受限，需要处理多进程写锁/忙等待；不能把单一逻辑写入者误解为全库只有一个进程写；WAL/Journal、锁等待、崩溃恢复、文件 ACL 和目标 Windows 兼容性仍需 P4 设计/验证 |
| B | Main Process 与 CardHost 分离文件存储，各自管理对应数据文件，以版本和对账机制保持一致 | 进程隔离清晰；单文件单写者较容易实现；CardHost 可独立持有展示状态文件 | 跨文件事务和备份恢复复杂；定义/展示状态一致性需要补偿和对账；格式演进与并发写入需自行处理 |
| C | 嵌入式文档数据库（如 LiteDB） | 文档模型灵活；对象映射直接；可减少部分关系表设计 | 多进程并发/锁行为、存储引擎维护、兼容性和恢复能力需额外核验；与当前部署/运行时尚无匹配证据 |
| D | 其他方案，由用户补充技术或约束 | 可适配特殊环境约束 | 需重新评估部署、并发、恢复、迁移、维护和兼容性，可能增加 P3 收敛成本 |

## 3. 助手推荐

- 推荐：A（SQLite 本地数据库）。
- 理由：FolderHub 首版是 Windows 本地桌面应用，核心数据为结构化配置、目录记录、卡片定义和展示状态；SQLite 可提供事务、迁移和备份基础，避免自行维护文件格式。它与 ADR-035 的逻辑所有权可共存，但必须在 P4 明确跨进程连接/锁定策略，不能假定 SQLite 多写者无冲突。
- 推荐置信度：中高。依据是本地桌面结构化数据场景；缺口是目标运行时/部署方式、并发负载及 Windows Server 目标版本尚未完成实测。
- 可能改变推荐的因素：确认的运行时不兼容、实测写入竞争无法满足可靠性要求、部署环境禁止数据库文件或出现备份/恢复约束。

## 5. 最终确认结论

用户选择 A：采用 SQLite 本地数据库作为 FolderHub 首版物理持久化后端。该选择与 ADR-035 共同约束逻辑聚合写入权；Main Process 仍只写其拥有的业务主数据/全局设置/CardDefinition，CardHost 仍只写 CardPresentationState。

本选择不预先确定数据库表结构、ORM、SQLite 具体版本/封装库、Journal/WAL 模式、连接池、busy timeout、跨进程事务边界、加密方案、备份文件格式和恢复 SLA；这些属于 P4 详细设计或后续验证事项。未经目标环境验证的兼容性仍标记 `NEEDS_VALIDATION`。
