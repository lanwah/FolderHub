## 1. 问题背景

ADR-034 已确认每个交互式用户会话一个 CardHost；ADR-035 已确认 Main Process 与 CardHost 按逻辑聚合划分单一写入者。P3-05 已定义逻辑消息方向、幂等、版本、重连对账及跨聚合补偿，但尚未选择物理 IPC 传输。

## 2. 需要确认的问题

**Main Process 与同一交互式用户会话内的 CardHost，应采用哪一种本机 IPC 传输技术？**

本问题只选择传输机制，不选择序列化库、数据库、运行时、UI 框架、消息业务语义或完整安全实现。

## 3. 候选选项 V1

### A. Windows Named Pipes（命名管道，推荐）

- 优点：Windows 原生；支持双向流；不需要端口分配/防火墙规则；支持 DACL/ACL；适合同机低流量命令/响应/事件。
- 缺点/代价：需自行定义消息帧、超时、取消、重连和连接生命周期；端点命名与实例发现需要设计。
- 风险：默认 DACL 不够严格；命名管道可支持远程访问，若未拒绝远程客户端可能扩大攻击面；仅限制同一用户/会话仍不能自动阻止同会话恶意进程冒用。
- 必要控制：显式 DACL；User SID + Logon SID；拒绝远程客户端；验证 PID/SessionId/令牌/进程来源；连接 nonce/实例令牌；载荷校验。

### B. Local RPC（ncalrpc）

- 优点：Windows 原生本地 RPC；本地端点语义明确；适合定义较强类型的调用接口。
- 缺点/代价：IDL/存根、端点注册、部署诊断和调用模型更复杂；托管集成门槛高于 Named Pipes。
- 风险：RPC endpoint ACL、认证/模拟级别配置错误会造成越权；需更专门的维护经验。

### C. TCP loopback（127.0.0.1）

- 优点：语言/框架无关；容易复用 HTTP/gRPC 等协议与调试工具；未来跨设备扩展较自然。
- 缺点/代价：端口发现/占用、监听生命周期、防火墙/安全软件交互和额外认证机制；需要强制仅绑定 loopback。
- 风险：localhost 不是身份认证；端口被其他本地进程抢占/仿冒；错误绑定可能暴露网络接口。

### D. Shared Memory + Event/Mutex

- 优点：大块数据吞吐高、拷贝少。
- 缺点/代价：需自行实现缓冲区布局、同步、背压、崩溃恢复、版本兼容和内存映射生命周期；控制命令仍需消息协议。
- 风险：共享状态崩溃后难以诊断；命名对象 ACL/会话隔离仍需严格配置。当前数据量无明显理由承担该复杂度。

### E. 其他

用户可提出其他技术，并说明安全、兼容性、复杂度和验证依据。

## 4. 助手推荐

- 推荐：A. Windows Named Pipes。
- 置信度：中高。
- 理由：当前场景为同机、双向、低流量、Windows-only 通信；Named Pipes 原生支持并可配置 ACL，不需要端口或网络监听；与 ADR-034 的每会话 CardHost 进程模型匹配。
- 依据：Microsoft Learn 的 IPC 机制比较、Named Pipes、Named Pipe Security、CreateNamedPipeW；P3-03/04/05；ADR-034/035。
- 依据缺口：最低目标 OS（Server 2012/2012 R2）的实际 ACL、Logon SID、远程拒绝、进程身份核验和重连语义仍需 PoC。

## 5. 兼容性与安全特别说明

- Microsoft 当前文档列出 .NET Framework 4.8 可安装于 Windows Server 2012/2012 R2/2016；但 Server 2012/2012 R2 已 out-of-support。技术兼容不代表操作系统仍获安全支持。
- Named Pipe 默认安全描述符可能授予 Everyone 和匿名账户读取权限，必须使用显式 DACL，不得使用默认权限作为安全设计。
- 必须拒绝远程客户端，并按 Logon SID 限定终端服务会话；仍需验证同用户同会话进程冒用防护。
