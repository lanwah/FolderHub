## 1. 问题背景

ADR-021 已确认全局 Keep Cards 开关默认 ON：Main Process 正常退出后 CardHost 继续显示卡片。ADR-034 已确认每个交互式用户会话一个 CardHost；ADR-035 已确认 CardHost 独立写入 CardPresentationState；ADR-036 已确认 Named Pipes 为 IPC 传输机制。

现有需求明确“主程序退出后卡片继续显示”，但没有定义：**Main Process 已退出、Keep=ON 时，如果 CardHost 自身崩溃，FolderHub 是否必须自动恢复卡片？** 这会决定是否增加常驻 Supervisor/其他恢复代理、进程数量、部署维护复杂度和卡片中断时间。

## 2. 需要确认的问题

Main Process 已退出且 Keep Cards=ON 时，如果 CardHost 意外崩溃，首版应采用哪种恢复策略？

本问题只确认 CardHost 异常后的恢复行为/责任机制，不改变正常退出时 Keep ON/OFF 的既有产品规则，不决定具体重启次数/间隔 SLA。

## 3. 候选选项 V1

### A. 不增加常驻监督进程；下次 Main Process 启动时恢复（推荐）

- 行为：CardHost 崩溃后当前卡片暂时不显示；CardPresentationState 以最后成功持久化状态保留；用户下次启动 Main Process 时重新启动 CardHost 并恢复卡片。
- 优点：不新增常驻进程；架构、部署、升级和故障排查最简单；与当前已确认需求边界一致，不承诺未确认的自动恢复 SLA。
- 缺点/代价：Main Process 已退出期间发生 CardHost 崩溃，卡片不会自动回来，直到用户再次启动主程序。
- 风险：用户可能误以为 Keep=ON 包含宿主崩溃后的自动恢复；需要在设计/诊断中明确“正常主程序退出保留”与“宿主崩溃恢复”是不同场景。

### B. 增加每会话轻量 Supervisor，CardHost 崩溃后自动重启

- 行为：每个交互式用户会话由独立 Supervisor 监控 CardHost；即使 Main Process 已退出，Supervisor 仍可按受控退避策略重新启动 CardHost 并恢复卡片。
- 优点：更接近用户对持续可见性的预期；主程序退出期间也能自动恢复。
- 缺点/代价：新增常驻进程、会话启动/退出管理、Supervisor 自身故障恢复、升级和回滚复杂度；需防止无限重启和重复实例。
- 风险：Supervisor 自身崩溃、升级版本不匹配、权限边界错误可能扩大故障面；额外资源成本尚未测量。

### C. Windows Service + 每会话 GUI Agent

- 行为：Windows Service 负责监督/协调，交互式用户会话中的 GUI Agent 启动或恢复 CardHost。
- 优点：可集中管理监督逻辑。
- 缺点/代价：Service 与 Session 0、用户会话 GUI Agent、权限/安装/升级/回滚协调复杂；对当前单用户交互式桌面场景可能过度设计。
- 风险：Session 0 隔离和跨会话授权错误；服务不可直接承载可见桌面卡片。
- 当前判断：除非后续明确需要服务级监督或多用户管理，否则不推荐。

### D. 其他

用户可提出其他恢复机制或可靠性要求。

## 4. 助手推荐

- 推荐：A. 不增加常驻监督进程；下次 Main Process 启动时恢复。
- 置信度：中。
- 理由：SRS v0.11 / REQ-BL-1.0 只确认 Main Process 正常退出时 Keep=ON 卡片继续显示，并未要求 CardHost 崩溃后自动恢复或定义恢复时限。A 可满足已确认需求且不引入额外进程；若用户认为宿主崩溃后也必须自动恢复，可选择 B 并承担其资源、部署和维护成本。
- 依据：ADR-021、ADR-034、ADR-035、ADR-036；P3-03 §5/6；P3-06 v0.2。
- 依据缺口：尚无 CardHost 崩溃率、用户可接受中断时间、Supervisor 资源开销及目标 OS 自启动可靠性 PoC。
